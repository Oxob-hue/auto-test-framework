# 测试设计说明

> 本文档说明本项目用例的设计思路，用于面试展示「测试设计能力」与「工程化思维」。
> 对应被测对象：Petstore 接口（RESTful）+ SauceDemo Web（UI）。

---

## 1. 测试分层与关注点

| 层级 | 关注点 | 说明 |
|------|--------|------|
| 接口层（API） | 协议正确性、状态码、数据结构、业务规则 | Petstore 宠物「增删改查 + 状态流转」 |
| 页面对象层（PO） | 元素定位与页面行为封装 | 定位器集中、页面跳转封装（如 `go_to_cart` 返回 `CartPage`） |
| 用例层（tests） | 场景编排与断言 | 只表达「业务意图」，不接触定位细节 |

## 2. 用例设计方法

### 2.1 正反向用例分离
- 每个功能点至少一对正/反向用例，并用 `negative` marker 标注反向用例，方便按需运行；
- 示例：登录成功（standard_user）vs 登录失败（锁定账号/密码错误/空用户名/空密码）。

### 2.2 等价类与边界（接口）
以宠物状态字段为例：

| 类别 | 取值 | 用例 |
|------|------|------|
| 有效等价类 | available / pending / sold | `test_find_pets_by_status` 参数化 3 条 |
| 无效等价类 | 不存在 ID | `test_get_non_exist_pet`（404）、`test_delete_non_exist_pet`（404） |

ID 采用时间随机生成，覆盖「大数/重复执行」场景的同时保证用例可重复运行。

### 2.3 异常与幂等清理
- 每条创建类用例在 `finally` 中删除数据（幂等），保证环境可重复运行、不残留脏数据；
- 模块级 fixture `created_pet_id` 负责前置创建与整体清理，数据生命周期与用例组绑定。

### 2.4 数据驱动
- 参数化数据统一放 `test_data/`，用 `PROJECT_ROOT`（pathlib）定位，与启动目录解耦；
- JSON 一组数据 = 一个独立场景（覆盖三种状态），新增场景只需加数据、不改代码。

### 2.5 响应结构约束（schema）
在字段断言之外引入 `jsonschema` 校验（`test_data/pet_response_schema.json`），
约束字段类型 / 必填项 / 枚举范围 —— 防止前后端字段漂移导致「用例绿但契约已坏」。

### 2.6 UI 业务规则校验
- 排序正确性：按价格升序后，断言**页面实际展示**的价格列表升序（而非只断言下拉框被选中）；
- 购物车数量：加购 N 件 → 角标 N → 购物车条目 N，端到端数量一致；
- 表单校验：缺少邮编时断言停留在原页并出现指定错误文案。

## 3. 稳定性设计（失败重试策略）

pytest.ini 配置：失败自动重试 1 次，**但仅对基础设施类异常重试**：

```ini
--reruns 1 --reruns-delay 1
--only-rerun "(WebDriverException|TimeoutException|ConnectionError|ReadTimeout|...)"
```

设计理由：浏览器/驱动/网络抖动属于环境噪音，可重试消除；
**断言类失败（AssertionError）不重试**，避免用重试掩盖真实缺陷 —— 这是稳定性和有效性的平衡点。

## 4. 失败可观测性

用例失败时自动在 Allure 报告中附加：
1. 运行日志尾部（`logs/test.log` 最近 300 行）；
2. Web 页面截图（PNG）；
3. 页面 DOM 源码。

实现：单一 conftest 中的 `pytest_runtest_makereport` hook（全项目仅注册一次）。

## 5. 环境与配置管理

- 配置集中在 `config.ini`（地址/驱动/浏览器/等待超时/无头模式）；
- 支持环境变量覆盖 `TEST_<SECTION>_<KEY>`（如 `TEST_WEB_HEADLESS=true`），
  使 CI 与本地共用同一套用例与配置，无需改代码。
