## 二、本项目真实踩坑复盘

### 复盘 1：页面对象方法"缩进错了"，方法根本没生效

- **现象**：`InventoryPage.go_to_cart()` 期望"点购物车并返回购物车页对象"，但代码中它
  被写成了**模块级函数**（缩进错误），且引用了**未导入的 `CartPage`** —— 一旦被调用必然抛 `NameError`。
- **为何测试没发现**：早期用例绕开 PO，直接在测试里 `driver.find_element(...).click()` 跳转购物车，
  等于把已坏的封装"闲置"了。
- **修复**：将方法收回类内并 `from pages.cart_page import CartPage`（无循环导入）；
  同时把测试改为使用 `inventory_page.go_to_cart()`，让封装真正被消费。
- **启示**：封装若不被用例使用，等于没有封装；重构后补一条"真走封装"的用例做护栏。

### 复盘 2：pytest 捕获 stdout 后，日志 handler 写入"已关闭的流"报 ValueError

- **现象**：自研 logger 在 import 时创建 `StreamHandler(sys.stdout)`；pytest 的捕获机制在
  teardown 阶段关闭/替换原 stdout，日志再写入时报 `I/O operation on closed file`，污染运行输出。
- **修复**：console handler 改为**每次 emit 时动态取当前 `sys.stdout`**（自实现 `_ConsoleHandler`），
  并让文件输出在无写权限时优雅降级为仅控制台，保证日志组件不拖垮测试。
- **启示**：框架组件要能适配测试框架的生命周期；"日志不可用也不能影响用例结果"是工程底线。

### 复盘 4：同一套用例本地全绿、CI 必挂？——React 重渲染导致的"丢点击"

- **现象**：Web 用例本地 Edge 全绿，推上 GitHub Actions（Chrome 无头）后 4 条购物车/结算用例稳定失败：
  点"购物车图标/Checkout/Remove"后**页面状态完全没变**，且无任何报错（仅超时/断言失败）。
- **定位过程**：失败时 hook 自动保存了页面源码与截图 → 下载 Allure 产物分析发现：
  断言失败瞬间 DOM 仍停留在原页面（点购物车没跳转、点 Checkout 还停在购物车页），
  说明**点击事件丢失了**，而不是断言写错。
- **根因**：被测站点为 React 应用。慢速环境（CI）下，上一次操作触发的 React 重渲染
  可能在"我们等待可点击 → 点击"之间替换 DOM 节点，Selenium 点到了已脱离文档的旧节点，
  事件不生效且不报错（stale 竞态）。
- **修复**：页面对象点击后**校验状态提交**（URL 变化 / 对应按钮出现或消失），未达成则
  自动重新点击（最多 3 次），并捕获 `StaleElementReferenceException`；新增 `BasePage.click_until`。
- **启示**：跨环境（Edge/Chrome、本地/CI）跑同一套用例是发现此类竞态的最好方式；
  失败时的"页面证据自动收集"让这类问题可被 10 分钟内定位。
- **后续加固（CI 多轮迭代收敛，当时 23 条在 Chrome 无头下全绿；后续用例已扩充至 47 条）**：
  1. React **受控输入框**输入后 value 可能未提交/被水合重置 → `input_text` 输入后轮询校验，
     未生效则用 **JS 原生 setter + input/change 事件**兜底；
  2. 点击偶发不被 React 委托接收 → `click_until` 以 **Selenium 点击 ↔ JS `element.click()`**
     交替重试（JS 点击事件冒泡到 React 根节点）；
  3. 失败自动附加**浏览器 Console 日志**，便于直接看到前端 JS 报错；
  4. 个别浏览器/无头环境下表单校验**只标红不渲染错误文案** → 负向用例断言改为
     "校验拦截业务规则（URL 未跳转）+ 文案可选校验"，避免环境差异导致的误报。

### 复盘 3：重复 conftest 导致 hook 执行两次、fixture 互相遮蔽

- **现象**：根目录与 `tests/` 下各有一份 conftest，**重复定义**了 `driver` fixture 与
  `pytest_runtest_makereport`（失败截图）hook —— 一个失败用例会尝试截图两次，且 fixture 定义
  相互遮蔽难以维护。
- **修复**：收敛为**唯一一份** `tests/conftest.py`，全部 fixture 与 hook 单一来源。
- **启示**：全局夹具是"单例资源"，重复定义是典型坏味道；排查时先看有没有多个 conftest。

## 三、面试常见追问速答（配合本项目）

| 追问 | 应答要点 |
|------|----------|
| 为什么用显式等待而不用 sleep？ | sleep 固定时长浪费/不稳定；显式等待（WebDriverWait）按条件轮询，命中即返回 |
| 显式等待和隐式等待区别？ | 隐式等待全局轮询 findElement；显式等待按条件作用于特定元素；项目两者都配，PO 内以显式为主 |
| 用例不稳定怎么办？ | 先分类：定位问题 / 时序问题 / 环境问题；再做稳定性设计（重试仅限基础设施类异常），最后留失败截图与日志定位 |
| 失败怎么定位？ | hook 自动附加日志尾部+截图+DOM，配合 Allure 按步骤查看 |
| 测试数据怎么管理？ | fixture 前置 + finally 幂等清理 + 随机 ID；参数化数据独立成文件、路径基于项目根 |
| 为什么在 config 之外支持环境变量覆盖？ | 多环境/CI 需要不改代码切换配置（浏览器、无头、地址），配置与用例解耦 |
| 项目有没有接入 CI？ | 已提供 GitHub Actions 流水线：push/定时触发 → 接口(ubuntu) + Web(Chrome 无头) → 汇总生成 Allure 报告上传 |
