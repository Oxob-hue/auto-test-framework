## 二、2 分钟项目讲解（口头版，约 600~700 字）

> 我介绍一下自己独立完成的全栈自动化测试框架项目。
>
> 项目被测对象有两个：**Petstore 公开接口**和 **SauceDemo 电商网站**，一个验证接口层、
> 一个验证 UI 层。目前是 **23 条用例全部通过**，接口 12 条、Web 11 条。
>
> 框架整体是**四层架构**：测试用例层 → 页面/接口对象层 → 公共封装层 → 配置层，
> 类似 Page Object 的思路，定位器集中维护、页面跳转有封装，改页面元素时用例代码基本不用动。
>
> 接口这部分，我用 Requests 做了统一封装：Session 复用、统一超时、自动打印请求和响应日志；
> 断言上不只看状态码，还会校验**业务字段 + jsonschema 结构**，防止前后端字段悄悄变化
> 用例还一直绿。测试数据是通过 fixture 前置创建、用例结束自动清理，ID 随机生成，
> 所以整套用例**可以反复跑、不残留脏数据**。
>
> Web 这部分覆盖登录的正反向场景、购物车、商品排序、以及一条**从登录到加购、结算、下单成功**
> 的完整 E2E。
>
> 项目里我印象最深的是**稳定性攻坚**：本地 Edge 上一直全绿，推到 GitHub Actions 用 Chrome
> 无头跑就必挂。我靠框架里"失败自动收集截图、页面源码、浏览器日志"的能力做了定位，
> 发现是 **React 应用的重渲染/水合竞态**——点击或输入落到了被替换的旧节点上，事件丢失但不报错。
> 解决办法是**每次点击、输入后都校验状态是否真的提交**（比如 URL 变了没有、按钮是否出现），
> 没生效就换 JS 方式自动重试。这样迭代了几轮，最后在 CI 上全绿。
>
> 另外我把它接到了 **CI/CD**：GitHub Actions 上接口在 Linux 跑、Web 用 Chrome 无头跑，
> push 或每天定时触发，通过后自动生成 **Allure 报告并发布成在线网页**，也就是简历里那个链接。
>
> 最后一点是文档和流程：我沉淀了测试设计说明、测试计划、报告模板和缺陷复盘，
> 算是把"设计 → 执行 → 报告"的完整闭环走了一遍。
> 这个项目让我体会到，自动化测试不是写几个脚本，而是**稳定、可观测、能进工程体系**的质量方案。

## 三、讲解 cue 卡（紧张时看要点）

1. 一句话定位：接口 + Web 双端框架，23 条用例全绿，已接 CI 与在线报告；
2. 架构：四层 + PO，改元素不改用例；
3. 接口：三层断言 + 数据"前置创建/自动清理/随机 ID"；
4. 亮点故事：React 在 CI 不稳定 → 证据定位 → "点击输入后校验状态 + JS 兜底" → 收敛全绿；
5. 可观测：失败自动收集 日志/截图/DOM/Console，重试只针对环境类异常；
6. CI/CD：Actions 多 Job、Chrome 无头、定时触发、Pages 在线报告；
7. 收尾：测试设计/计划/报告文档化，体现完整流程意识。

## 四、常见追问速答（精简版）

| 追问 | 怎么答 |
|------|--------|
| 为什么用例能重复跑？ | 数据前置在 fixture、结束在 finally 清理、ID 随机；就算失败也会清理，不残留 |
| 失败重试会掩盖 bug 吗？ | 只对浏览器/驱动/网络类异常重试，断言失败不重试——真实缺陷不会被重试"洗绿" |
| 本地绿、CI 挂怎么排查？ | 先看失败时框架自动收集的截图/DOM/Console；我那次发现是 React 丢点击，不是断言错 |
| 怎么防止元素变更导致用例挂？ | 定位器集中在页面对象；失败会留页面源码快速定位；还有唯一 conftest 保证 hook 不重复 |
| CI 报告怎么自动更新的？ | 用例跑完由 allure 生成报告 → GitHub Pages 部署 Job 发布；只有测试全绿才更新在线版 |
| 接下来想学什么？ | 想了解测试平台化/关键字驱动，以及用大模型辅助生成与维护用例（结合你团队现状聊） |
